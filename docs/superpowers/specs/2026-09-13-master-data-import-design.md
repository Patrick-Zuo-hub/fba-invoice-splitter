# 主数据表格导入设计

## 目标

在主数据抽屉中支持上传一份主数据表格，一次性刷新运输渠道、送货仓库与 FBA 仓库。

目前这三类数据只能在界面上逐条录入，批量更新靠临时脚本完成（`~/.fba-invoice-splitter/backups/` 里 `fis-before-master-import` 一类的备份即是佐证）。便携版分发后使用者没有命令行也没有 Python，界面导入是唯一可行的更新途径，因此该功能必须先于打包完成。

## 输入格式

以现有的 `赤道物流_主数据` 表格为模板，按 **Sheet 名称**匹配，不依赖顺序：

| Sheet | 首行表头 | 数据列 | 目标表 |
| --- | --- | --- | --- |
| `FBA仓代码&详细地址` | `FBA仓代码` / `FBA仓详细地址` | A=仓代码，B=详细地址 | `fba_warehouses` |
| `渠道` | `渠道` | A=渠道名 | `shipping_channels` |
| `国内交货仓` | `国内交货仓` | A=仓库名 | `delivery_warehouses` |

首行必须是表头，从第二行开始读取数据。空行跳过。缺少任一 Sheet 或表头不符即整体拒绝，不做部分导入——宁可报错也不要悄悄只更新一部分。

送货仓库表只有名称一列，地址留空（数据库允许送货仓库地址为空）。

## 合并策略

**Upsert：只增不删。**

- 文件中有、库中无 → 新增。
- 文件中有、库中有且内容不同 → **以文件为准覆盖**。这是刻意偏离现有的"重复不覆盖地址"行为：上传的表格是权威版本，否则地址更新永远同步不进来。
- 库中有、文件中无 → **保留不动**。历史批次按名称引用渠道与仓库，删除会使既有记录出现悬空引用。代价是废弃条目会一直留在下拉框里，可由使用者手动停用。

仓代码沿用现有的 `canonical_amazon_warehouse_code` 归一化，以免 `ONT8` 与 `AMAZON-ONT8` 被当作两条。

`app_defaults` 中按仓库学习到的渠道偏好不受导入影响。

## 事务边界

整份表格在一个事务内写入。任一行失败则整体回滚，库停留在导入前的状态。这样失败的导入不会留下半新半旧的主数据。

## 结果反馈

导入后在抽屉内显示每一类的新增与更新条数，例如：

```
FBA 仓库：新增 110，更新 8
运输渠道：新增 10，更新 0
送货仓库：新增 0，更新 0
```

未变化的条目不计入任何一项。上传失败时保留现有的红色错误提示样式。

## 安全边界

沿用发票上传已有的约束：仅回环访问、`X-FIS-Request` 头校验、大小上限、通过 `SafePackage` 读取压缩包以防 zip 炸弹与路径穿越。表格内容一律按数据处理，不解析公式，不跟随外部链接。

## 验证

- 解析层：三个 Sheet 的正常读取、缺 Sheet、表头不符、空行、仓代码归一化。
- 合并层：新增、覆盖、保留缺失项、计数正确、失败回滚。
- 路由层：安全头校验、体积上限、错误提示。
- 端到端：用与真实模板同构的合成表格走完上传到计数展示。

测试夹具为合成表格，不提交任何真实主数据。
